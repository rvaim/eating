# ADR-0013 无历史消息与可配置投递队列

状态：Accepted

日期：2026-10-27，Asia/Shanghai。

确认来源：负责人明确“不需要历史记录，太庞大了”，并要求队列存储方式可选，在全局设置侧栏及二级分类中配置队列上限、等待新消息等参数，采用准确名称。下面的默认数值和实现细节属于本轮实施选择，可在界面修改，不代表负责人逐项固定这些数值。

## 背景与边界

旧版incoming_events兼任聊天历史、去重与待投递队列，可靠接收后仍保留原文和原始协议包。可靠投递不要求Eating长期复制Harness会话历史，因此应分离传递责任和长期保留。临时实时日志仍只在可见日志页签订阅，不落盘、不补历史。

本决策补充ADR-0010的数据保留方式，不替代其正式Host、OneBot与独立MCP原则；ADR-0006的认知边界和ADR-0012的独立包边界继续有效。

## 决策

1. Eating不建设聊天历史库，删除本地历史页面及qq_list_received_messages工具；标准OneBot按ID读取get_msg仍可使用。
2. 只有尚未完成交接的规范化Harness信封进入有限队列，不另外保存原始OneBot事件或正文列。无需转交的消息不保存正文。
3. 队列可选本地暂存或仅内存。前者跨重启恢复；后者不将正文写盘，重启丢失未交接内容。运行时切换迁移现有队列，失败不得部分更新模式、版本或正文。
4. 每条消息同时计入条数与UTF-8字节容量；满时按已选策略拒绝新消息或移除最旧pending。正在交接和结果未知的消息不自动移除；不静默假装已经入队。旧积压超过新默认限额时保留既有消息并明确提示超额，拒绝继续增长。
5. 静默时间从同会话末条更新，最长等待从首条固定；条数或目标体积可提前触发。批次不混合不同会话，保留逐条ID和来源。批次体积为目标，单条过大时单独投递、不拆分，仍受队列硬容量限制。
6. 仅接收端明确提供accepted、durable及有效receiptId，才能视为已可靠接手并删除本地正文；这不等于模型已读、轮次结束、任务成功或外部动作完成。异常/超时不自动重发；只有明确拒收才有限冷却重试。
7. 短期去重只保留有界哈希标识和回执摘要，不保存正文；发送请求的防重复记录独立保留，避免清空队列后重新发送已执行动作。
8. 全局设置分为“消息投递”和“队列与存储”。设置按版本原子保存，冲突保留草稿，重新读取须明确放弃未保存修改；清空队列另行明确确认，正在交接时拒绝清空。

## 默认实施参数

本地暂存；队列1000条及10MiB；满时拒绝新消息；聚合静默500ms、最长等待2000ms、单批10条、目标32KiB；接收回执超时15000ms、明确拒收重试间隔10000ms、最多尝试5次。界面可修改，验证相关的交叉约束。

容量是队列信封的UTF-8字节，不是整个SQLite文件、模型Token或完整工作区磁盘配额。短期去重常态上限10000个、24小时，完整SQLite清理故障期间有界内存兜底使总上限最多20000个小标识，无正文。

## 迁移与影响

事务迁移旧库，保留pending/delivering/uncertain的未交接内容；启动时在途转待核对。清除终态历史及raw/text副本，删除旧表，在同库回收空间，不创建第二份聊天备份。账号实例配置、MCP凭据、插件安装信息与发送防重复记录不迁移或清空。

旧版Host不会读取新队列表，不能在仍有未交接内容时直接降级并假设队列可见；回退必须先安全交接或采用明确的反向迁移。已按用户要求删除的历史正文不承诺恢复。
