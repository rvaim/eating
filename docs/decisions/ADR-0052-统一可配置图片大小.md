# ADR-0052：统一可配置图片大小

状态：Accepted，2026-11-10，源码及云端保留数据部署完成。负责人要求把 Eating 本地的 5 MiB 图片上限改为可配置，默认 10 MiB。验证与交付状态见[本轮报告](../reports/2026-11-10-图片大小配置验证报告.md)。

## 根因

5 MiB 是 Eating 的本地限制，分散于公开图片资源、QQ 下载／发送、MCP image 结果、生图输入／输出和表情库。只改上传入口会继续被下游拦截；单独提高原图限制还会被原先固定的 Base64／JSON 预算截断。它不是 OpenAI 或 OneBot 对所有图片的统一规定。

图片库索引的格式有效性与当前操作限额必须分离。否则主人调低上限后，重启可能把合法的历史大图误判为损坏，无法管理整个库。

## 当前契约

Host 管理一份独立 `host:image-limits` 设置：严格 `{schemaVersion:1,revision,maxImageMiB}`。首次缺省使用 10 MiB，读取不补写。主人通过“设置 → 图片大小”调整为 1–50 的整数；API 使用 session／CSRF 与 `expectedRevision` CAS，不提供模型修改工具。无效格式拒绝且保留原数据，不修改插件配置或迁移图片索引。

公开 SDK 的 `HostPluginContext.imageLimits()` 读取当前不可变快照；纯函数 `imageLimits()` 统一计算上限。对 Eating 自带生图、表情库、QQ 收图／发图和图片预览生效，PNG、JPEG、WebP、GIF 同限：

| 边界 | 计算方式 |
| --- | --- |
| 单图 | `maxImageMiB × 1048576`，默认 10 MiB |
| 单批原图总量 | 单图的 2 倍，默认 20 MiB，最多 4 张 |
| 可信图片 Base64 预算 | `ceil(batchBytes / 3) × 4 + 16`，含逐图 padding 余量 |
| QQ 最终 wire | `max(encodedBytes, 4 MiB 音频预算) + 1 MiB` |
| 主人上传请求 | `ceil(imageBytes / 3) × 4 + 1 MiB` |
| 生图提供商 JSON 响应 | `ceil(imageBytes / 3) × 4 + 1 MiB` |

QQ 扣除后台核验的可信媒体之后，普通参数仍限 1 MiB；入站、响应及 WebSocket 接收上限保持。模型不能自行传预算、文件路径或任意下载地址。共享目录逐图校验也使用当前上限，unknown 不更换传输重发。

存储元数据和原始图片验证采用独立的 50 MiB 支持上限，管理／预览／发送采用主人当前限额。调低设置不删除或改写已有图片，仍能列表、编辑元数据、显式删除；超限预览和发送拒绝，调高后可重新读取。修改设置使旧发送 lease 失效，发送前复核 revision。

已经接受的生图任务固定使用提交时的单图大小及容量预留，不因主人随后调整而扩大请求或丢弃已付费结果；完成后保存原图，后续取图受当前限额约束。不改变每次一张、库总量 256 MiB、任务／图片数量限制，也不增加付费重试。

## 版本与范围

应用／Host／Web 0.21.0，plugin-sdk 4.11.0，QQ 0.16.0、生图 0.4.0、表情包 0.3.0。其余 SDK 产物消费者按封存规则补丁升级：DSH 0.18.2、记忆 0.3.2、语音 0.1.1。ui-sdk 4.2.1、plugin-core 4.0.0、插件 API4 保持；无新依赖或锁文件变化。

提供商、模型与 QQ／OneBot 仍可能拒绝更大图片。通用 direct MCP 的独立 10 MiB 传输信封、第三方 Harness／服务的限额不属于本次内置资源设置，不承诺随之扩容。GIF 按原始格式传输；本次不增加生图的动图参数。

本决策替代 ADR-0037、ADR-0046 中固定的图片 5／10 MiB 及可信图片 14／15 MiB 预算；其中权限、来源、回执、防重和共享目录规则保留。历史报告中的当时数字不改。操作见[图片大小设置](../operations/图片大小设置.md)。
