# ADR-0061：QQ语音引用直传

日期：2026-11-14。状态：已采纳。补充ADR-0060的当前输入契约，格式防漏仍保留。

## 根因与证据

QQ0.17.1实际运行，主子系统消息和工具目录均已含格式规则。原生日志显示05:11的语音发送参数message依旧是序列化的record数组字符串，收到QQ_MESSAGE_FORMAT_INVALID／not-sent后没有改成真实数组；随后改用CQ及猜测附件路径，出现OneBot1200。11点之后只回复历史失败的解释，没有再次尝试正确语音调用。模型声称传入真实数组及没有音频文件，均与实际参数和资源不符。

通过当前正式资源preview接口只读读取了两条原有音频，分别53804字节／1120ms和234284字节／4880ms，WAV、字节和asset身份校验均通过。缺少音频文件不是本次根因。

通用message同时支持字符串、数组及对象，原先把选择正确嵌套结构交给模型；增加提示和拒绝错误参数，只能防止误发，不能确保真实模型会自行纠正。先前系统DSH回环使用脚本模型，能证明错误传递及正确结构可通，不能证明实际模型会按同样步骤恢复。

## 当前决定

- 沿用qq_send_private_message、qq_send_group_message和qq_send_message，增加明确的顶层audio_ref字符串。message与audio_ref必须且只能提供一种；audio_ref不能与auto_escape同时传入，也不能是路径、URL、Base64、CQ或JSON。
- audio_ref只接受SDK当前完整eating-audio URI。QQ后端明确构造一条record数组，删除Eating输入字段后进入原发送链路。这是新输入契约，不解析错误JSON、不推断字符串类型、不回退传输。
- 账号实例、私聊／群聊目标、当前授权scope保持原校验；音频仍经Host getAudioAsset lease读取，核对WAV／长度／摘要及实时撤权，转换Base64后交给OneBot。模型不获得音频字节或主机路径。
- 发送账本使用规范化后的OneBot参数；audio_ref同号重复只投递一次。已成功／unknown保持原幂等，不换号、不重新合成、不改为别的传输重发。原先在账本前拒绝的格式请求可用同号纠正。
- speech_get输出明确audio_ref；原有sendable继续表达当前标准OneBot消息段，非旧格式读取或自动迁移。历史成功任务在读取时获得新返回字段，不改写索引或生成新音频。
- 主／私聊／群聊与TTS说明优先指向audio_ref，错误明确该参数。不得把旧失败、猜测路径失败或没有正确调用，解释为当前资源缺失／语音通道损坏。
- 面板显示两种内容输入与互斥说明；已有语音只填引用，文字／标准消息仍填message。中英文、窄屏、确认与请求ID行为保持。
- QQ0.18.0、TTS0.2.1；应用、SDK和其他五插件保持。无需新工具权限、数据迁移或自定义提示词重置，无新外部依赖或锁文件变化。

## 验证与部署

验证公开发送schema和真实资源链路，覆盖同号、撤权及unknown；实际系统DSH私聊／群聊、已安装QQ／TTS浏览器联合发送，音频仅生成一次、投递一次。发布后应验证正式安装后台读取原有4.88秒音频，在隔离OneBot回环构造原字节record。不能将回环通过表述为真人QQ播放实测。

按GitHub同提交构建、私有全量备份和原data更新。原配置／索引／音频／图片／数据库／会话／日志前缀保持。实数与边界见[报告](../reports/2026-11-14-QQ语音引用直传修复部署报告.md)。
