# ADR-0063：JPEG结构校验与尾部数据

日期：2026-11-14。状态：已采纳。修正QQ入站图片按文件最后两个字节识别JPEG的实现。

## 已证实根因

正式QQ0.18.0在同一图片两次读取及再次引用时均返回MEDIA_INVALID_IMAGE／“图片字节与声明的图片格式不匹配”。正式get_msg与下载成功：HTTP200、Content-Type=image/jpeg、283131字节。JPEG真实结束位置是283107，后面另有24字节。macOS ImageIO完整解码为1279×1706，像素缓冲8727896字节。工具在返回MCP图片前误拒绝，模型没有获得这次图片内容。

原detectedImageMime只接受FF D8 FF开头且整个文件最后两字节是FF D9，混淆JPEG码流结束与下载文件结束。重发同一图不修复这个校验条件。原图、签名URL、真实消息ID、原始日志仅留项目外私人诊断目录，不提交用户照片。

## 决定

在QQ插件内新增线性、非递归的JPEG结构读取器。按段长度跳过APP／COM等内容，识别帧与扫描头、组件及尺寸，扫描数据区处理字节填充、重启间隔与重启标记，沿结构到达EOI。结构依据[ITU-T T.81附录B](https://www.w3.org/Graphics/JPEG/itu-t81.pdf)，标记位于段边界，APP／COM内容中的同值字节不作为结束标记。

仅完整帧／扫描及真实EOI后允许外层尾部数据；无帧／无扫描／无扫描数据、缺失EOI、段越界／非法长度、无效组件与尺寸、错误扫描和重启标记仍拒绝。基线及渐进式多扫描都验证。校验针对码流结构，不声称实现完整JPEG熵码解压或发现每一种像素编码损坏。

QQ返回原始全部字节、MIME及实际下载大小，不截尾、不转码、不重新编码、不换图、不按尾部特征添加特殊分支。总大小上限涵盖尾部；现有HTTP MIME匹配、超时、响应编码、禁止重定向、不给图片域传认证头、账号／消息／资源配对与读前后撤权校验保持。

原生DSH在接收MCP图片后可能按官方附件实现优化／重新编码。本轮保持原生行为；验证分别断言QQ MCP原字节一致，以及最终模型实际收到JPEG图片输入，不宣称模型data URI必定与原文件逐字节相同。

## 发布与验证

只升QQ四处版本至0.18.1；应用0.25.0、SDK4.14.0、DSH0.21.0及其他六插件、依赖锁保持，无新外部依赖、数据迁移或人格／提示词覆盖。

测试使用原生解码过的自制1×1灰色基线／渐进JPEG；覆盖24字节尾部、APP／COM伪结束标记、扫描转义与重启、全部截断前缀、非法段／头以及HTTP大小／MIME。真实系统DSH链路验证HTTP下载→MCP图片→原生附件→模型请求；已安装浏览器验证JPEG实际解码。部署后直接对原消息进行只读取图，并在隔离的正式安装包／DSH回环中使用同一原图。

本地commit／push后，服务器从GitHub拉同提交构建；空闲停Eating、全量私有备份后同data更新，不重新初始化或删除历史。六个未变插件封存清单逐一核对。实数与证据见[部署报告](../reports/2026-11-14-JPEG尾部数据误拒绝修复部署报告.md)。
