# Eating 启动流程草案

状态：未实现的运行设计，字段与顺序未冻结，当前不要执行启动命令。来源：v0.3 §6.2、本轮插槽式架构确认。

1. 识别 Eating 专属数据根、数据版本与工作区；取得同一数据集的排他运行权，确认没有另一活跃主要认知控制者。
2. 读取用户选定的 Harness 适配器及已批准模块清单；校验核心人格、模型/记忆机制配置、凭据引用和批准范围。不得为补齐能力自动安装未批准扩展。
3. 打开运行存储，检查队列/动作账本；失败时不继续接受无法持久化的新事件。
4. 按 Eating 的扩展契约加载已批准模块，校验版本/依赖并分别注册后台能力与模块自己的管理界面。失败时回收本模块注册与资源，保留诊断，不清空其他模块注册。
5. 启动/恢复通讯模块，报告实际连接、补收能力和积压；Harness 未就绪时仅在可持久化的前提下继续接收。
6. 按选定适配器的配置与隔离要求启动/连接固定版本 Harness；核对实际数据/插件/工作区/凭据范围，避免继承用户其他实例配置。
7. 完成真实接口握手与 capabilities 检查，不用“进程存在”代替就绪；核对本方案所需的会话恢复、持久记录、事件投递、暂停/取消、调度及记忆能力。
8. 查找主身份与实际恢复句柄的映射，按已核接口恢复或首次创建；检查人格、工具和授权配置。恢复失败不得静默新建，不支持的接口不得模拟成功。
9. 检查上次未确认外部操作和旧控制者的在途活动，先核对真实状态，再决定是否补投；无法确认旧控制者已停止时不得激活新控制者。
10. 仅向一个当前活跃的主要认知控制者启用有记录的队列投递与已授权调度，展示就绪、降级或故障状态。

步骤是候选依赖顺序，不是已经冻结的并发启动方案。首次创建何时持久化、失败后的回收与通讯模块启动顺序将在实验后调整；DSH 是首个具体技术验证对象，其他 Harness 需分别核对，实际 Codex/Claude Code 接口尚未核实。

## 就绪、降级与停用

至少区分 Host、存储、模块注册、各模块后台/界面、选定 Harness 接口、主要认知控制者、恢复句柄（若支持）、通讯渠道、模型与记忆机制的状态。没有真实模型调用不能宣称模型可用；记忆机制须由所选 Harness 提供可用且经主人授权的能力，缺失/失败要报告，不冒充正常长期记忆。

能力查询需区分 `unsupported`（明确不支持）、`unknown`（未核或证据不足）和 `error`（本次探测/调用失败）；不能把失败当作不支持或正常。必要能力不足时不能声称整体就绪，可选模块失败应局限自身；共享 Host/存储故障仍可能影响整体。状态名和字段均是候选，见[接口契约](../technical/接口契约.md)。

停用或启动回滚时停止该模块新工作、撤销其后台与界面注册、处理在途调用并释放归属资源，保留未决队列/动作和必要配置；重新启用前先对账。卸载不默认删除用户数据，见[数据归属](../architecture/数据归属.md)。Cordis 仅为 Proposed 的 Node/TS 插件底座，其逻辑作用域不能证明进程或 OS 失败隔离，见[插槽式扩展](../architecture/插槽式扩展.md)。

## DSH 适配器：专属启动检查（源码分析）

使用独立 `DSH_HOME`、`DSH_AGENTS_HOME`、Profile 和工作区启动固定版本 DSH；两个 home 分别核对，避免继承用户主配置。SDK 创建/恢复不自动组合 Preset，必须另核 Agent 实际配置。`session()` 是惰性句柄，跨进程恢复按 `resumeSession(savedId)` 的真实语义验证，不能用持有 ID 代替恢复。证据见[源码核对](../research/DSH源码核对.md)，相关实验见 Phase 1/2；这些不是其他 Harness 的通用启动接口。
