# 原生网页 Fake-IP 拦截与图片声明诊断

日期：2026-11-01，Asia/Shanghai。用户反馈开启网页能力后，对百度、QQ和中国天气网的“网页获取”全部报 `URL hostname ... resolves to a non-public IP address`，并询问图片输入声明是否有效。本轮是实际根因与配置含义核查，不把功能已挂载等同于外网请求已经成功。

## 已确认根因

原5180/5181实例仍为DSH0.9.0、运行就绪。用户已经将web功能授给qq.private和qq.group。实际配置为：

```json
{
  "native-web-provider": {
    "searchProvider": "deepseek-official",
    "fetchProvider": "http"
  },
  "tool-web": {
    "search": false,
    "fetch": true,
    "fetchTimeoutMs": 30000,
    "searchTimeoutMs": 60000
  }
}
```

截图调用的是网页获取web_fetch；当前关键词搜索web_search没有启用。网页获取和关键词搜索虽然放在同一原生功能条目中，仍有各自的工具参数和提供商依赖，单独勾选web模块不等于已验证搜索服务。

使用系统DNS的实测结果：

| 域名 | 解析地址 | 普通系统网络HTTP GET |
| --- | --- | --- |
| www.baidu.com | 198.18.2.176 | 200，216ms |
| www.qq.com | 198.18.14.0 | 200，610ms |
| www.weather.com.cn | 198.18.23.163 | 200，1208ms |

三个地址均在198.18.0.0/15保留段，符合TUN/Fake-IP环境的特征。普通HTTP请求可由系统网络实际路由成功；原生 `dsh-web-fetch-http` 的直连路径先执行 `resolvePublicAddresses`，要求解析结果为公网单播，因而在发出HTTP请求前以 `WEB_BLOCKED_URL` 拒绝这些地址。模型Key、模型是否能思考、图片输入声明和网站服务器状态不能解释这一组错误。

公开原生实现的请求流程为：先查询 `proxyRouteFor(url)`；已明确配置HTTP代理的域名请求可交代理解析，否则先验证和固定DNS地址再请求。当前macOS的HTTP/HTTPS/SOCKS/PAC代理均未启用，诊断环境的HTTP_PROXY/HTTPS_PROXY/ALL_PROXY等均未设置；没有获得可信的显式代理地址，未猜测端口，也未修改系统网络。

## 原生配置边界与修复方向

直接使用系统安装的DSH，在临时独立HOME/DSH_HOME下运行配置schema导出，确认当前HTTP抓取器只提供：`maxResponseBytes`、`maxBodyChars`、`timeoutMs`、`maxRedirects`、`userAgent`。不存在 `allowPrivate`、`allowFakeIp` 或关闭DNS公网校验的原生配置项；不能建议填写不存在的参数或宣称改超时会解决地址预检查。

schema导出对AgentPreset树载体另有投影诊断，但目标HTTP提供商条目自身标记为schema且可解析其完整字段；本轮只使用该模块的字段证据，没有把整份schema导出称为无诊断通过。

当前正确修复方向是让此独立DSH实例使用明确的、原生支持的HTTP代理出口，或由抓取器提供明确支持系统TUN/Fake-IP的网络策略。后者涉及公网地址防护的语义，应使用清楚的当前契约；不改主DSH安装、不做未声明的模块覆盖、DNS重写或全局地址放行。本轮没有实际改动网络配置、代理、权限或抓取策略，网页获取仍处于已定位但未修复状态。

此前原生能力回归证明了模块、配置和模型工具挂载，并未覆盖用户真实TUN网络的成功抓取；该限制不能据此前回环通过而省略。

## 图片输入声明的实际作用

通过主人只读管理操作确认：`imageInput=true`，revision为1。当前运行的生成overlay中，模型输入确实为：

```json
{
  "input": ["text", "image"]
}
```

[适配器](../../plugins/harness/dsh/src/backend/adapter.ts)按声明生成模型输入元数据；关闭时为text，开启时为text和image。这不是一个只改变前端显示的选项。它使DSH能够将原生附件或获准MCP图片作为视觉输入送入支持图像的模型链路。

该声明不自动探测模型服务，不发付费测试，不为文本模型增加视觉能力，也不授予QQ图片工具或文件读取权限。实际识图同时要求图片来源/工具被授权、图片真实可读取，以及实际提供商/模型支持图像。模型名称本身不是支持证据；本轮未做真实提供商识图验证。

## 当前桌面DSH与Eating的实际对照

用户继续询问“为什么当前DSH不会、本项目会”。在当前桌面DSH会话通过它实际暴露的web_fetch工具，分别读取 `https://www.baidu.com/` 和 `https://wttr.in/`，两次均返回与Eating截图相同的non-public IP错误。当前系统DNS对百度仍返回198.18.2.176。因此同一原生网页获取路径在两边都会失败，不能概括成“主DSH的网页获取正常、只有Eating异常”。

只读核对桌面Profile的网页相关项：搜索提供商配置指向Magpie网关 `http://127.0.0.1:3425/v1`，凭据引用为MAGPIE_GATEWAY_KEY，模型为codex/gpt-6.1-sol；Eating的web功能则选择fetchProvider=http、search=false/fetch=true，搜索模块保持默认DEEPSEEK_API_KEY引用。搜索是调用提供商Messages服务的另一条链路，与本机HTTP抓取的DNS公网预检查分离。此配置对照不等于本轮重新验证了搜索服务可用；没有发送可能产生费用的辅助搜索请求，也没有复制主人主Profile或凭据到Eating。

结论：此前能搜索或能用其他工具访问网络，不足以证明相同web_fetch路径可用；本轮已直接复现当前DSH的相同错误。先前仅回答“DSH自带”没有说清楚具体提供商与工具路径，现补充该实证。抓取策略修复仍未实施，所有核查只读，不改主DSH、网络、权限或用户数据。

## 本轮操作与边界

- 只读取原实例的公共配置、原生能力目录、图片声明和不含明文Key的生成overlay。
- 对用户给出的三个公开网站做无凭据GET，读取响应状态后取消body，没有下载或记录页面正文。
- 使用临时独立profile核对系统DSH公开配置schema，不启动模型回合或创建用户会话。
- 没有修改模型配置、图片开关、原生权限、DNS、TUN、系统代理或主DSH；没有重启真实Harness，没有真人消息或付费模型测试。
- 无功能源码变更，本轮不重复运行全量构建/回归；后续修复应补真实网络路径的验证。
