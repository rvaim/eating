# 自主暂停与按钮文案只读诊断

日期：2026-11-10，Asia/Shanghai。用户要求搁置音色，核查自主运行截图中的 `resumeAfterReview`、错误暂停与全部成功的历史记录。本轮只读核查生产及隔离复现，没有修改代码、服务器配置、开关、历史或恢复自主运行，未调用真实模型、TTS或QQ发送。

## 已确认原因

服务器正式 `/api/autonomy` 与当前持久状态一致：`errorCode=AUTONOMY_RUN_LIMIT`、`ownerPaused=true`、`failures=0`、`mode=active`、`lastOutcome=completed`，最近一轮结束于2026-11-10 04:31:02。配置为 `maxRunMinutes=120`、`maxCyclesPerHour=12`、`minIntervalSeconds=60`。当前Harness及原生运行时就绪，六插件connected、队列0、托管服务异常重启0。当前轮次不是模型或工具失败，而是Eating的连续活动时长限制阻止了下一轮准入。

`DshAutonomy.claim()` 以 `now - state.startedAt` 检查120分钟。只有明确登记 `sleeping`／`waiting` 才结束活动段；只写“等待”说明文字不能改变真实mode。保持active期间的最短间隔和小时额度等待仍计入经过时间，因此不能将该限额解释成累计模型执行时间。

额度达到上限时，`claim()` 直接设置暂停与错误码并拒绝准入，没有创建新周期，没有调用 `finish()`，也没有追加history或覆盖lastOutcome。最近结果继续显示前一轮成功，历史全为completed与本次预算暂停并不矛盾。小时窗口过期后的snapshot又把本小时计数显示为0，它不表示连续活动预算已恢复。

前端将所有非空errorCode统一归为reason.error，显示“发生错误，已暂停”，没有区分预算限制与实际故障。具体errorCode只放在下方“更多运行详情”里，概览缺少直观原因。

恢复按钮调用 `t('resumeAfterReview')`，但自主运行的简中与英文资源均没有该键；i18next在两种语言都缺少值时返回键名，所以直接显示了内部标识。应补齐当前正式双语资源，不应添加吞错或隐藏缺失翻译的通用回退。

## 隔离复现

使用当前实际 `DshAutonomy` 与UI翻译实现、独立临时目录及可控时钟，按每小时12轮、每轮3秒模拟两个小时：

| --- | --- |
| 完成轮次 | 24，全部completed |
| 模拟模型轮次总时长 | 72秒 |
| active模式经过时间 | 120分钟 |
| 下一轮准入 | false，AUTONOMY_RUN_LIMIT |
| 连续失败次数 | 0 |
| 最近结果／保留20条历史 | completed／全completed |
| 重置后的小时计数 | 0 |

隔离重启还确认：runtime启动把startedAt清空，但保留预算暂停；因而runRemainingMs可重新显示完整额度，仍不会自动清errorCode或恢复。现场startedAt已为null，因此不根据当前快照倒推历史活动段的精确开始时刻；服务器暂停原因本身由持久errorCode明确证明。

## 推荐修正

补齐恢复按钮双语文案；概览按真实code区分“达到连续活动上限，已暂停”和实际故障，并直接显示120分钟这一原因。历史保留真实周期结果，不把预算暂停伪造为模型失败。若要将maxRunMinutes改成实际执行时长预算，需要明确改变计时契约，使配额等待与间隔不被混算；不能通过调大限额、清error或自动恢复掩盖现状。
