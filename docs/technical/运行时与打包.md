# Eating 运行时与打包

状态：Node.js/TypeScript Host 已实现；本轮按[单仓独立包与产物加载](../architecture/工程结构与插件发布.md)重组，相关构建、安装、独立 pack 与 UI 已于 2026-10-27 完成验证，详见[重组报告](../reports/2026-10-26-单仓独立包重组报告.md)。Tauri/Sidecar、真实 Harness 分发和三平台发行仍为 Proposed，未完成。

## 当前包与产物边界

一个仓库管理源码，主程序、SDK 与插件独立成包和发版；根 pnpm workspace 聚合开发、构建、测试。Host 与 Web 为独立应用，公开 SDK 当前 `1.0.0`、`apiVersion` 为 `1`；QQ `@eating/plugin-qq` `0.2.0` 独立交付后台、界面与校验清单，主程序不捆 QQ，运行不依赖仓库插件源码。目录和包名是本轮实施选择，已确认原则见 [ADR-0012](../decisions/ADR-0012-单仓独立包与插件加载.md)。

首期安装 CLI 接收本地构建目录，校验 API/SDK 兼容与文件哈希，暂存后原子发布到 `EATING_HOME/plugins/<pluginId>/versions/<version>` 并切换激活索引。安装、升级和卸载需先停止 Host，完成后重启；升级仅改目标插件，卸载保留原账号数据。Web 动态导入 Host 提供的界面资源，公开界面 SDK 和 React 共享宿主实例。已确定的 CLI 用法见[QQ 操作说明](../operations/QQ配置与功能测试.md)，仓库外产物已验证安装、官方 MCP、升级、删除构建源后重启与卸载数据保持，证据见[重组报告](../reports/2026-10-26-单仓独立包重组报告.md)。

这一步不包括运行中热更新、任意第三方市场下载或真实 npm 发布。可独立构建/加载也不代表目标 OS 的安装包、签名、公证、许可证或恶意插件隔离已验收。

## 候选桌面部署形态

Tauri Shell/React UI 与 Eating Host 分离，Host 管理已批准的通讯模块和用户选定的 Harness 适配模块；同一数据集只有一个当前活跃的主要认知控制者。DSH 是首个具体技术验证对象，不是永久唯一运行时；实际 Codex/Claude Code 接口未核，不能假设与 DSH 具有相同嵌入和分发方式。

Host 已采用 Node.js/TypeScript；Harness 的进程边界、是否共享分发运行时及如何受控提供包管理器仍待验证。不能把开发机已有 DSH、Node 或其他 Harness 当作完整用户发行方案。模块所需运行时、外部服务和安装步骤须单独核验，新增可执行能力仍需可信主人明确批准。

Cordis 是优先验证的 Node/TS 后台插件底座（Proposed），版本和最终采用未定；Eating 自己定义平台无关的扩展接口、前端注册机制及持久数据契约。Cordis 内部类型不自动成为跨进程协议，后台模块不直接依赖 React/浏览器；模块的后台能力与自己的管理面板分别注册/撤销。详见[插槽式扩展](../architecture/插槽式扩展.md)、[Cordis 选型评估](Cordis选型评估.md)与 [ADR-0008](../decisions/ADR-0008-Cordis候选底座.md)。

Cordis scope 只提供逻辑资源归属/清理，不是进程或 OS 沙箱。同进程模块可共享崩溃影响，真正的权限和失败隔离需按风险设计并验证，不能仅凭作用域宣称已达成。

## 打包清单待核

- 所选 Harness 适配器与真实发布包/固定源码版本的对应、完整性和兼容范围；内置、受控外部进程等方式需逐个核验。
- Node Host 的实际捆绑版本、目标 OS/架构、原生 ABI；各 Harness 所需运行时分别核对，根声明下限不等于捆绑版本。
- 包管理器的受控调用，不依赖用户 PATH；可安装插件所需网络/构建工具及批准范围。
- 通讯/Harness 模块的依赖、能力声明、后台/界面资源与版本兼容；QQ、飞书等同类模块不直接互相依赖。
- Tauri Sidecar 命名、签名、公证、权限、系统 WebView 与升级策略。
- 用户持久数据和只读安装资源分离，升级不覆盖人格、会话、记忆、授权、队列或未决动作。
- 所选运行时、Node、第三方 notices、各插件许可证和再分发条件。

本轮未核实全部运行时依赖、原生 ABI 或第三方分发条款，不承诺直接可打包，也不承诺跨 Harness 插件/会话/记忆兼容或无损迁移。

## DSH 适配器：打包核对示例

“内置 DSH”指 Eating 管理的独立运行环境，不意味着运行在 React 页面，也不必先把整个 DSH 桌面应用嵌入。Node Host 与 DSH 的进程边界、共享运行时方式仍未定，桌面应用内部安装路径不是稳定 SDK。

需核对 DSH 精确发布包与固定源码提交的对应、包完整性、官方 Node 实际捆绑版本、原生依赖与工具二进制，以及 Python/浏览器等按能力分发或批准安装的方式；根声明下限不是实际 Node 捆绑值。还需核对 DSH 的 MIT notices、第三方与插件各自许可。这些打包项尚未验证，不能泛化为其他 Harness 的依赖清单；已知 SDK 事实见[源码核对](../research/DSH源码核对.md)。

## 生命周期与模块移除

必须分别定义关窗口、隐藏到托盘、停止 Host、停止当前 Harness、停用某模块、完全退出和开机启动。托盘存活可先实验；UI 进程真正退出后继续运行需要独立后台生命周期，不靠持续 React 页面。UI 崩溃不应直接杀死主要认知控制者。

模块停用时停止新工作，撤销其后台/工具/页面注册、清理订阅与连接，按实际能力处理在途调用与远端调度；迟到响应不得恢复已撤销入口。移除模块的清理局限于自身，不能要求修改 QQ/飞书等其他模块或通用管理页，不能误删共享依赖。配置、队列、审计、恢复映射及未决动作按[数据策略](../architecture/数据归属.md)保留，卸载包不等于删除用户数据。

设备休眠时不能保证模型继续执行；恢复后需要核对调度与外部动作，避免重复。切换 Harness 前先确认旧控制者停止，不承诺运行中热切换。

## 三平台测量矩阵

Windows、macOS、Linux 分别记录 OS/架构、签名方式、安装包/安装后大小、首次启动、选定 Harness 就绪耗时、空闲内存/CPU、关闭窗口行为、动态模块/插件安装与撤销、升级回退。分别记录模块后台/界面、适配器和 capabilities 的版本及真实状态，不将 `unsupported`、`unknown`、`error` 记作已支持或调用成功；状态与字段名均为候选。阈值在基准后讨论，不虚构数值。

在没有开发环境的干净设备/镜像验证启动、权限、模型配置与批准安装；不能只凭开发机能运行通过。DSH 作为首个样本的结果不能代替其他 Harness 验证；三平台尚未构建或测量，见[Phase 5](../plans/路线图与PoC计划.md)。
