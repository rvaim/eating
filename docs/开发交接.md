## 设置与行为

设置存 Host settings，带 revision，与 QQ 账号配置分开。两个分类共用一份草稿，点击“保存设置”一起保存并应用；跨字段校验覆盖最长等待不小于静默、单批条数不大于队列条数、批次目标不大于队列容量。并发 revision 冲突返回 409、保留草稿，重新读取需确认放弃未保存修改。

| 消息投递 | 单批消息上限 | 10 条 |

按 `conversationId` 聚合，同会话新消息重置静默计时，最长等待从首条入队固定计时。达到条数/目标字节提前，单条大于目标时独立、不拆分；目标是软阈值，不代表模型 token 或上下文上限。批次接收端用 `deliverBatch`，旧 `deliver` 按批内事件逐条交付，不能把后者写成一次模型请求。设置作用于之后选择，已在途交接沿用开始时的超时。

只有接收端返回 `accepted: true`、`durable: true`、非空 `receiptId`，且本地 ack 提交成功后，才删除队列正文并累计可靠交接数；不代表模型已消费。明确拒收才按间隔有限重试；超时、抛错、凭据不足、重启中断或重试耗尽保留为结果待核对，不自动补投。

## 存储不变量与关键 API

[HostStore](../apps/host/src/store.ts)不再建设聊天库。`delivery_queue` 只持有当前 outstanding 的规范化 Harness JSON；原 OneBot raw、额外 text 副本、不转交消息的正文均不保存。`event_dedup` 仅哈希、小状态/时间和回执哈希，固定 24 小时、常态合计不超过 10000 个；SQLite 连清理也持续失败时，旧磁盘标识加故障内存缓存上限合计 20000 个。故障 RAM 去重无法保证跨重启，错误与拒收计数必须可见。

- `getQueuedHarnessEvents()` 返回全部 pending/delivering/uncertain，按 sequence 升序；快照独立解析，接收端改写不能污染 RAM。
- `getDeliverySettings()`、`getDeliverySettingsSnapshot()`、`updateDeliverySettings(values, expectedRevision)` 使用公开 SDK 校验。持久模式统计通过 SQL COUNT/SUM 聚合元数据，内存模式直接累计 Map，不为工作区定时汇总读取大正文。
- `markHarnessDeliveryBatch()` 批次事务更新，delivering 增尝试数，pending 带下次重试时间；`acknowledgeHarnessBatch()` 原子删除正文、记小回执与计数，重复 ack 不多计。
- `clearDeliveryQueue()` 有 delivering 时 409；用户确认后删除其余正文、计 discarded，保留账号配置、去重与发送账本。`pendingHarnessEvents()` 仅返回当前可尝试的 pending；`listMessages()` 只供未交接诊断，raw 为 `{}`，不返回终态历史，不作为 QQ 页面或 MCP 历史入口。

容量按规范化 JSON 的 UTF-8 字节和全部 outstanding 条数，不能写成整个 SQLite 文件最多 10 MiB。reject-new 满时新正文不保存，`recordEvent` 返回 `inserted: true / queued: false / admission: rejected`，计数与 `lastQueueError` 可见，QQ 实时日志仍可记录接收准入结果。drop-oldest 只移最旧 pending，保护 delivering/uncertain；超大单条先拒，不清空原队列。缩容若保护状态仍超限，整次 409，设置、模式和正文均保持。模式切换准备好目标存储后事务提交，写失败不丢原队列。

外发 `actions` 执行、进程内锁、持久结果、作用域与 unknown 语义保持。移除聊天历史或清空临时队列都不能删除这个发送防重复账本。

## 旧库迁移与真实升级

首次打开旧库时，在事务中保留全部 pending/delivering/uncertain 的有效信封；delivering 启动恢复为 uncertain。终态消息只可留下未过期的小哈希，旧正文、raw/text 副本与 `incoming_events` 删除，设置 schema 版本；之后原库一次 VACUUM/checkpoint，不额外备份聊天。旧 backlog 超默认容量也保留，通过 overCapacity 提示并拒新。新库启用 incremental auto_vacuum，正文删除时回收与 checkpoint。详情见[数据规范](technical/数据目录与账号实例.md)。

**真实升级已完成并通过 API 核验。** 主流程停止旧 QQ 0.3.0 job，在工作区锁内迁移旧库并安装 QQ 0.4.0，唯一新开发 job 为 `bash-3a6f5eac4f134a3f`。原 3 条未交接信封逐一规范化 JSON 指纹一致，新队列 3 条/2587 字节；旧历史表删除，无聊天备份。账号配置、实例索引哈希和 actions 稳定键指纹保持。实际 API 确认 QQ 0.4.0、connected、logsSupported=true、工具 9 且无历史工具；设置接口 200、revision 0、本地暂存，Harness 仍 not-attached。

最终构建、自动回归、真实迁移与安装均已完成，运行与截图证据见[验证报告](reports/2026-10-27-投递设置与无历史队列验证报告.md)。续接使用当前新 job 与原实例，不再启动旧服务；不在文档或报告写个人正文和令牌。源码回退不能恢复已删除历史或内存退出丢失的正文，旧 Host 依赖旧表，不可直接用旧二进制打开迁移后的库。

## 保持的产品边界

Eating 不生成 AI 回复、不建立第二套 Agent Loop 或长期人生记忆。当前没有真实 Harness 接收者或 DSH 插件；独立 sink 只验证交接契约。MCP 可用不代表认知接入，可靠接收不代表模型已读。可替换 Harness 与完整迁移仍按[Harness 设计](architecture/Harness适配.md)区分已实现与 Proposed。

本版仅一个默认账号实例，不支持多账号并行；QQ 空间、反向 WS、远程暴露、Tauri、Windows/Linux 和完整恶意插件 OS 沙箱未完成。开发使用普通 Node，不改 DSH 签名或当前 GUI；bundled Node 的原生库 TeamID 不符问题不通过重装或改签规避。文档任务不操作真实 home、登录或向真人自动发消息。
